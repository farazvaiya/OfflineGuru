## 2. Intended execution chain (as implemented)

For LLM specialist agents invoked via harness:

1. **Agent definition/prompt:** role sections in `engineering_team/agents/AGENTS.md`; role aliases/names in `config/team.toml` and `claude_runtime.load_role_definition()` (`claude_runtime.py`).
2. **Orchestrator:** `Orchestrator.execute_agent(agent, task_id, ...)` in `harness/orchestrator.py` loads task, calls adapter, validates artifacts, records workflow event, returns continuation decision.
3. **Harness adapter:** `ClaudeCodeAdapter.run()` in `harness/claude_adapter.py` dispatches to attached runtime when no local handler registered.
4. **Runtime:** `AgentExecution.run()` in `harness/claude_runtime.py` performs availability check, loads role definition, provisions isolated workspace (`WorkspaceProvisioner.seed`), acquires writer lock, builds prompt, constructs argv (`claude -p ... --output-format json --max-turns ... --add-dir <ws>` + `permission_args`), plans sandbox, executes subprocess (no shell), captures bounded output, classifies status, collects artifacts/source-change metadata, writes execution log, persists `agent_runs`.
5. **Workspace/permissions:** `harness/workspace.py` seeds allowlisted source snapshot into per-run `source/` + `artifacts/` (inspect frozen/read-only for read-only roles, edit copy for implementation roles; track-aware path for `track='A'/'B'`), computes digests; `harness/permissions.py` enforces per-role tool allowlists/modes, env allowlist, containment, optional bwrap sandbox.
6. **Persistence:** DB schema/migrations in `harness/db.py` (`agent_runs`, `workflow_events`, `tasks`, `experiments`, `benchmarks`, `evaluations`, `decisions`, etc.); `paths.py` resolves state paths at call time (`ENGINEERING_TEAM_ROOT` honored).
7. **Downstream workflow phases:** separate orchestrator methods manage state transitions and records: `record_root_cause`, `record_baseline`, `start_dual_track`, `record_benchmarks`, `run_evaluation`, `prepare_decision_report`, `approve/reject/request_tests`, `integrate_approved` (`orchestrator.py`, `state_machine.py`, `evaluator.py`, `benchmark.py`, `report.py`).

## 4. Harness-bypass / direct-execution observations

- **Direct `claude` CLI invocation inside harness:** only in `engineering_team/harness/claude_runtime.py` via `subprocess.run` (intentional runtime). No other `claude` subprocess invocations found in harness code outside runtime/tests/docs.
- **Agents never invoking an LLM / simulated:** all specialist LLM labor depends on `claude_runtime` availability; if runtime unavailable or no handler/runtime, adapter returns `pending_external`/`NOT_CONFIGURED` without fabricating success. Main DB shows no successful real runs.
- **Hardcoded/simulated outputs:** present in test fixtures and in our controlled E2E fake CLI (explicitly labeled). No production hardcoded success path found in runtime.
- **Outputs never consumed / missing execution records:** controlled test shows successful agent runs produced artifacts/logs/DB rows but **tasks remained open** and no automatic downstream consumption occurred; this is a real handoff/orchestration gap.

## 5. Overall audit conclusion

`engineering_team/` contains a substantial, partially implemented harness with real runtime plumbing for Claude CLI agent execution (workspace isolation, permissions, logging, DB persistence) and programmatic workflow/evaluation/reporting components. **Harness integration is present at the component/API level but not proven as a fully autonomous, end-to-end, multi-agent coordinated system using real LLM executions.** Key gaps are autonomous orchestration/handoff, consumption of agent outputs into workflow/task state, and evidence of real LLM runs and real QA test execution.
